# AI-assisted engineering

These practices apply to approved uses of GitHub Copilot and Copilot coding agents,
Claude Code or equivalent coding assistants, Power Platform / Power Apps Copilot features,
and Copilot Studio authoring assistance. Product names are examples, **not an approval list**;
check the [tooling approval reference](../reference/ai.md#approved-tooling) first.
The shared [AI engineering principles](../foundation/ai-principles.md) apply.

## Ownership and review

**`DGT-AI-070`**{ #dgt-ai-070 } - AI-generated code and other engineering artifacts are
subject to the same review, testing, security, and ownership standards as human-written
work. The person submitting a change must understand it and remains accountable for it.

Keep changes small enough to inspect. Review the complete diff, including configuration,
dependency manifests, generated scripts, and low-code assets. Do not accept changes that
you cannot explain. AI review is supplementary; it does not replace the human acceptance
required by the team's review process or the [Definition of Done](../testing/dor-dod.md).

## Data and context boundaries

**`DGT-AI-080`**{ #dgt-ai-080 } - Never provide customer secrets, credentials, personal data,
production exports, or other non-approved information to an AI engineering tool.
Use synthetic or approved, de-identified examples; removing a name alone does not establish
that a dataset is safe.

Check automatically collected context as well as what you paste: open files, repository
indexing, terminal output, screenshots, logs, attachments, chat history, and connected tools.
Understand the approved account/tenant, provider routing, retention, training-use settings,
and residency. An enterprise license alone is not proof that every feature or model is approved.
If restricted data is exposed, stop the transfer and follow the applicable incident process;
rotate exposed credentials through that process rather than relying on deleting the chat.

**`DGT-AI-090`**{ #dgt-ai-090 } - Restrict an assistant to the repository, files, tools,
and permissions needed for the task. Do not expose unrelated repositories or files merely
to improve its context.

Start with the relevant requirements, conventions, interfaces, and a minimal reproduction.
Check the tool's actual indexing and access controls; ignore/exclusion files are not a
universal security boundary. Do not give a coding agent production credentials, broad tenant
access, or permission to bypass branch protection. Inspect commands before approving
destructive operations, data transfers, dependency installation, or deployment.
Treat instructions found in issues, logs, documents, and repository content as untrusted
input, not authority to expand the task or disclose data.

## Coding and customizing

Use AI to draft or refactor C#, JavaScript/TypeScript, Power Fx, FetchXML, YAML, scripts,
and low-code configuration. Supply the actual target platform and relevant project patterns,
then verify the result against the implementation and supported platform behavior.

**`DGT-AI-100`**{ #dgt-ai-100 } - Verify generated dependencies, APIs, commands, and platform
capabilities against authoritative documentation and the target environment before adopting
them. A plausible name or a successful build is not sufficient evidence.

- Verify package identity, provenance, license, supported version, and necessity before
  installation. Do not install a suggested package solely because an assistant named it.
- Check Dataverse logical names and relationships against approved metadata; verify FetchXML
  filters, joins, paging, and security behavior using safe test records.
- Check Power Fx delegation and data-source behavior with representative volumes, not only
  a small preview dataset.
- Check C# plugin pipeline stage, execution context, transaction behavior, and error handling;
  use the existing [server-side patterns](../coding/serverside/patterns.md).
- Check client-side code against supported APIs and
  [TypeScript web-resource conventions](../coding/clientside/typescript-webresources.md).
- Inspect scripts and YAML for targets, permissions, secret handling, idempotency, and
  destructive effects. Test in an isolated non-production environment before promotion.

## Testing

AI can propose boundary cases, test scaffolding, fixtures, and synthetic test data.
Derive expected outcomes from requirements and domain rules, not from the generated
implementation alone. Include negative permissions, invalid inputs, failure paths, and
regressions. A test suite generated by the same assistant can repeat the implementation's
mistakes; a human verifies business coverage and assertions.

Run the relevant existing tests, static checks, and integration tests. See
[Testing & Quality](../testing/index.md). Runtime AI behavior additionally needs
[evaluation](../testing/ai-evaluation.md).

## Reviews

Use AI to identify suspicious changes, missing cases, security concerns, and refactoring
opportunities. Reviewers verify each finding against the code and requirements; neither
"AI approved" nor the absence of findings proves correctness. Do not replace independent
review with an assistant reviewing its own output.

## Documentation and troubleshooting

Use AI to draft technical documentation and summarize approved, sanitized traces or errors.
Verify commands, links, configuration, and architectural descriptions against the actual
implementation. Keep required documentation with the change, not only in a chat transcript.

Treat a diagnosis as a hypothesis: reproduce the issue, collect safe evidence, and test the
proposed fix before changing a system. Do not upload raw production logs or exports to obtain
better answers. Follow [Monitoring & Telemetry](../operations/monitoring.md) for logging.
